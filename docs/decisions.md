# 설계 결정 기록

v2에서 고른 것, 채택하지 않은 대안, 그 선택으로 감수하는 것을 적습니다. 결정이 바뀌면 지우지 않고 아래에 이어 적습니다.

## 1. 앱마다 독립된 package (npm workspaces를 쓰지 않음)

- **고른 것**: `apps/web`과 `apps/api`가 각자 `package.json`과 `package-lock.json`을 가집니다.
- **채택하지 않은 대안**: 루트에 lock 파일 하나를 두는 npm workspaces.
- **이유**: 두 앱이 공유하는 코드가 없습니다. lock 파일이 나뉘어 있으면 의존성 권고의 예외 목록을 앱별로 관리할 수 있고(웹 14건, API 0건), 이미지 빌드 컨텍스트가 앱 폴더 하나로 끝납니다.
- **감수하는 것**: 루트에서 한 번에 설치·테스트하는 명령이 없습니다. 역할 이름 같은 작은 타입은 양쪽에 따로 둡니다.

## 2. 토큰은 API가 발급하고 검증한다

- **고른 것**: API가 로그인 때 서명 토큰을 만들고 요청마다 직접 검증합니다. 웹은 토큰을 httpOnly 쿠키에 보관하고 API에 전달만 합니다. 서명 키는 API에만 있습니다.
- **채택하지 않은 대안**: 웹이 세션을 발급하고, API에는 웹이 서명한 짧은 수명의 토큰을 따로 보내는 방식.
- **이유**: 채택하지 않은 대안에서는 API가 "웹이 보냈다"는 것만 확인하므로, 웹이 침해되면 임의의 사용자로 요청할 수 있습니다. 고른 방식에서는 웹이 침해돼도 실제로 로그인한 사용자의 토큰만 전달할 수 있습니다.
- **감수하는 것**: 토큰이 유출되면 만료 전까지 클러스터 안 어디서든 쓸 수 있습니다. API는 호출한 쪽이 웹인지 확인하지 않습니다. 호출자 확인은 서비스 간 통제 단계에서 추가합니다.

## 3. API 테스트는 `node --test`로, 빌드한 결과물을 띄워서 한다

- **고른 것**: `tsc`로 빌드한 `dist/main.js`를 별도 프로세스로 띄우고 `fetch`로 요청합니다. DB는 실제 PostgreSQL입니다.
- **채택하지 않은 대안**: Nest.js 12 기본 템플릿의 vitest + supertest(테스트 안에서 Nest 앱을 직접 생성).
- **이유**: 테스트용 의존성이 늘지 않습니다. 배포될 결과물과 같은 것을 검사하고, 웹 테스트와 형식이 같아 v1 권한 매트릭스와 한 줄씩 대응시킬 수 있습니다.
- **감수하는 것**: 테스트 전에 빌드가 필요합니다. Nest의 테스트 모듈로 의존성을 바꿔 끼우는 단위 테스트는 하지 않습니다.
- **2026-11-27 추가**: 테스트 파일을 하나씩 차례로 실행합니다(`--test-concurrency=1`). 신청 요청과 취소 요청을 보내는 테스트가 생겨서, 파일들이 같은 DB를 동시에 바꾸면 목록 전체를 비교하는 테스트가 실패합니다. 전체 실행 시간은 약 1.7초에서 4.7초가 됐습니다.

## 4. Nest CLI와 기본 템플릿의 부가 구성을 쓰지 않는다

- **고른 것**: 빌드는 `tsc`만 씁니다. 기본 템플릿의 `@nestjs/observe`(외부 관측 서비스 연동), `@nestjs/mau`, 린트·포맷 도구, vitest는 넣지 않았습니다.
- **이유**: 외부 서비스를 쓰지 않는다는 저장소 규칙이 있고, 의존성 하나하나가 감사 대상입니다. API의 lock 파일은 263개 패키지이고 high 이상 권고 예외가 없습니다.
- **감수하는 것**: `nest generate`, `nest start --watch` 같은 편의 명령이 없습니다.

## 5. 린트는 아직 넣지 않았다 (넣을 예정)

- **현재**: 두 앱 모두 린트가 없습니다. 타입 검사는 `tsc`의 `strict`가 합니다.
- **넣을 것**: API 코드가 쌓인 뒤 CI 잡으로 추가합니다. 대상 규칙은 `await` 누락(`no-floating-promises`), `eval` 계열 금지, React의 HTML 직접 삽입 금지(`no-danger`)입니다.
- **미룬 이유**: 검사할 API 코드가 거의 없는 시점에 넣으면 설정만 늘고 걸리는 것이 없습니다. 도구(ESLint, oxlint)는 위 규칙을 지원하는지 확인한 뒤 고릅니다.

## 6. 의존성 설치 스크립트를 실행하지 않는다 (API)

- **고른 것**: API는 `npm ci --ignore-scripts`로 설치합니다.
- **이유**: 설치 스크립트는 패키지를 받는 순간 임의의 코드를 실행합니다. 설치 스크립트가 있는 패키지는 `prisma`와 `@prisma/engines` 둘이고, 실행하지 않아도 `prisma generate`, `prisma migrate deploy`가 동작하는 것을 확인했습니다.
- **감수하는 것**: 설치 스크립트가 필요한 패키지를 추가하게 되면 이 결정을 다시 봐야 합니다.

## 7. Prisma CLI의 하위 의존성 `effect`를 수정 버전으로 고정한다

- **상황**: `prisma@7.10.1` → `@prisma/config@7.10.1`이 `effect@3.20.0`을 정확한 버전으로 요구하고, 이 버전에 high 권고(GHSA-7589-6fvf-x4pw, 정규식 서비스 거부)가 있습니다. 감사 게이트가 이를 잡았습니다.
- **고른 것**: `package.json`의 `overrides`로 같은 메이저의 수정 버전 `effect@3.22.5`를 씁니다. 그 뒤 `prisma generate`, `prisma migrate deploy`, 테스트가 통과하는 것을 확인했습니다.
- **채택하지 않은 대안**: 예외 목록에 사유와 만료일을 적고 통과시키기. `prisma`는 개발용 CLI이고 이 저장소의 설정 파일만 읽으므로 예외로 둘 근거는 있었지만, 고칠 수 있는 것은 고치는 쪽을 택했습니다.
- **감수하는 것**: Prisma가 시험하지 않은 버전 조합입니다. Prisma가 의존성을 올리면 `overrides`를 지웁니다.

## 8. PostgreSQL은 18.7을 쓴다

- **고른 것**: `postgres:18.7-alpine3.24`를 다이제스트로 고정합니다. 로컬 `compose.yaml`과 CI가 같은 값을 씁니다.
- **채택하지 않은 대안**: 19.0. 메이저의 첫 릴리스라 고르지 않았습니다.

## 9. v2의 결함은 인증 계층으로 정하고, 결함마다 커밋 세 개와 태그 두 개로 남긴다

- **고른 것**: 결함 다섯 개를 인증 계층(Guard의 적용 범위, 요청 로그, 토큰을 보관하는 위치, HTTP 메서드)에서 고릅니다. 결함마다 테스트, 결함, 수정 커밋을 같은 브랜치에 두고 결함 커밋과 수정 커밋에 태그(`v2-defect-N`, `v2-fix-N`)를 붙입니다. 결함은 그 결함이 들어갈 기능을 만드는 브랜치에서 다룹니다. 목록은 [v2-defects.md](v2-defects.md)에 있습니다.
- **채택하지 않은 대안 1**: v1의 인가 결함(역할 확인 누락, 소유자 확인 누락)을 Nest.js로 다시 구현하기.
- **채택하지 않은 대안 2**: v1처럼 `vulnerable`과 `fixed` 두 브랜치를 두기.
- **이유**: 대안 1은 v1의 반복입니다. 인증 계층은 v1에서 전제로만 두고 결함으로 다루지 않았는데, API를 분리하면서 Guard, 요청 로그, 토큰 전달이 새로 생겨 결함이 들어갈 자리가 생겼습니다. 대안 2는 의존성을 올릴 때마다 두 브랜치를 같이 고쳐야 하고, 결함 상태를 가리키는 브랜치가 계속 남습니다.
- **감수하는 것**: v2에는 인가 결함이 없습니다. 소유자 확인은 v1 `fixed`의 정책 함수 방식을 API로 옮기고 테스트로만 검증합니다. 결함을 모아 보려면 태그 다섯 쌍을 차례로 봐야 합니다. 결함 커밋에서 테스트가 실패한다는 것은 CI 기록에 남지 않고 PR 설명에만 남습니다.
- **변경 1 (범위)**: 입력 처리 결함 세 개(SQL 인젝션, 저장형 XSS, request body의 사용자 id 신뢰)를 더해 여덟 개가 됐습니다. 마지막 것은 인가에 속하므로, 위의 "v2에는 인가 결함이 없습니다"는 "v1에서 다룬 두 유형(역할 확인 누락, 조회할 때 소유자 확인 누락)을 반복하지 않습니다"로 바뀝니다.
- **변경 2 (순서)**: "테스트 → 결함 → 수정"을 "결함이 든 구현 → 확인 → 테스트 → 수정"으로 바꿨습니다. 제대로 만든 코드에 결함을 나중에 넣으면 수정 커밋이 되돌리기가 되고, 결함을 찾아서 고치는 흐름이 기록에 남지 않습니다. 바꾼 순서에서는 결함 상태를 띄워 재현한 결과를 진단 보고서로 남깁니다. 태그는 그대로 결함마다 두 개입니다.

## 10. 이 저장소의 문서에서 RBAC은 앱의 역할을 뜻한다

- **고른 것**: 문서에서 RBAC이라고 쓰면 앱의 역할(학생, 강사, 관리자)로 정하는 규칙을 가리킵니다. ABAC은 요청한 사람과 대상의 속성을 비교하는 규칙(신청의 소유자인가, 그 강의의 담당 강사인가)을 가리킵니다. 둘 다 `apps/api/src/authz/policy.ts`의 `can()`에 있습니다.
- **이유**: 쿠버네티스에도 RBAC(Role, RoleBinding)이 있고, 2단계에서 그것을 따로 다룹니다. 같은 낱말이 두 계층에 있어서, 쿠버네티스 쪽은 항상 "쿠버네티스 RBAC"이라고 적어 구분합니다.

## 11. 여러 명이 동시에 신청해도 정원이 초과되지 않도록 행 단위 락을 쓴다

- **문제**: 정원 검사를 "신청 수를 조회하고, 정원보다 적으면 삽입한다"로 만들면 두 요청이 동시에 올 때 정원을 넘습니다. 두 요청이 모두 삽입 전의 신청 수를 조회하기 때문입니다. 정원이 1명이고 신청이 없는 강의에 요청 A와 B가 동시에 온 경우입니다.

  락이 없을 때:

  | 순서 | 요청 A | 요청 B |
  |---|---|---|
  | 1 | 신청 수 조회: 0명 | |
  | 2 | | 신청 수 조회: 0명 |
  | 3 | 삽입 | |
  | 4 | | 삽입 |

  정원이 1명인 강의에 2명이 들어갑니다.

  행 단위 락을 쓸 때:

  | 순서 | 요청 A | 요청 B |
  |---|---|---|
  | 1 | 강의 행에 락 | |
  | 2 | 신청 수 조회: 0명 | 락 대기 |
  | 3 | 삽입, 커밋 | 락 대기 |
  | 4 | | 강의 행에 락, 신청 수 조회: 1명 |
  | 5 | | 409 |

  정원이 1명인 강의에 1명만 들어갑니다.

- **고른 것**: 신청 요청을 처리할 때 그 강의의 행에 행 단위 락(row-level lock)을 겁니다(`SELECT … FOR UPDATE`, pessimistic locking). 락을 건 요청이 끝날 때까지 같은 강의의 다른 신청은 기다립니다. 락, 신청 수 조회, 삽입은 트랜잭션 하나로 처리합니다. 코드는 `apps/api/src/enrollments/enrollments.service.ts`의 `create`입니다.
- **중복 신청**: 같은 학생이 같은 강의를 두 번 신청하는 것은 `(userId, courseId)` 유일 제약으로 막습니다. 동시에 온 요청도 DB가 한쪽을 거부합니다.
- **채택하지 않은 대안**:
  - 버전 번호로 충돌 감지 (optimistic locking): 락 없이 진행하고 충돌하면 다시 시도합니다. 신청이 한 강의에 몰리면 충돌과 재시도가 많아집니다.
  - 트랜잭션 격리 수준 SERIALIZABLE과 재시도: DB가 충돌을 감지해 한쪽을 실패시킵니다. 실패한 요청을 다시 시도하는 코드가 필요합니다.
  - 신청 수 컬럼과 조건부 `UPDATE`: 강의에 신청 수를 저장하고, 정원보다 적을 때만 1을 더하는 `UPDATE`를 실행합니다. 검사와 증가가 한 문장이라 가장 빠릅니다. 신청 수가 두 곳(컬럼, 신청 테이블의 행 수)에 있게 되어 취소할 때 함께 맞춰야 합니다.
  - 세 대안은 구현해 보지 않았습니다.
- **이유**: 처리 순서(락, 조회, 삽입)가 코드에 그대로 보입니다. 신청 수를 한 곳에만 저장합니다. 락이 DB에 있어서 API 인스턴스가 여러 개여도 적용됩니다.
- **확인**: 정원이 1명인 강의에 학생 4명이 동시에 신청하는 테스트를 10회 반복합니다(`apps/api/test/enrollments-write.test.mjs`). 매번 201은 1건이고 나머지는 409입니다. `FOR UPDATE`를 제거하면 이 테스트가 실패하는 것을 확인했습니다.
- **감수하는 것**: 같은 강의에 대한 신청은 순차 처리됩니다. 다른 강의의 신청은 기다리지 않습니다. 부하 테스트는 하지 않았습니다.
